### 1-2. 패리/듀얼 중심 잼 게임 — 호평·불만

## 4. RIPOSTE에 주는 시사점 (10개 이내)

1. **관찰**: Boss Rush Jam 심사는 Fun/Theme/Boss Design/Controls/Art/Sound 6개 축을 따로 채점하며, 상위권은 이 축들이 고르게 강하고 하위권은 한 축(특히 Controls·Sound)만 약해서 밀린다 [[출처]](https://itch.io/jam/boss-rush-jam-2024/results/winners). **RIPOSTE 상태와의 차이**: RIPOSTE는 자체 테마 잼이라 "Theme" 축 자체가 없을 수 있고, 사운드는 WebAudio 합성음뿐이라 별도 확인 필요. **제안**: 참가할 잼의 실제 채점 축을 사전 확인하고, itch.io 페이지 문구·스크린샷 캡션을 해당 축(특히 Boss Design·Controls)에 맞춰 작성 — 코드 변경 아닌 페이지 작업.

2. **관찰**: 상위 잼 게임 다수가 스크린샷/설명에서 "규칙을 한 줄로" 전달한다(예: Titan Souls "화살 1개, 피격 1번"). **RIPOSTE 상태와의 차이**: RIPOSTE의 "내 공격은 0개, 패리로 훔쳐서 되쓴다"는 후크는 강력하지만 itch.io 페이지가 아직 없어(CLAUDE.md 기준 "확인 필요") 이 후크가 전달되는 경로가 없다. **제안**: itch.io 페이지 최상단에 이 한 줄 후크 + GIF 1개를 배치 — README 4장 스크린샷을 재사용하면 신규 에셋 제작 불필요.

3. **관찰**: Between Gods 리뷰에서 "패리 판정 창이 적마다 다르고 관대하지 않다", "텔레그래프가 잘 안 읽힌다"는 불만이 구체적으로 확인됐다 [[출처]](https://itch.io/jam/dis-august-2026-mutual-feedback-jam/rate/4832129). **RIPOSTE 상태와의 차이**: RIPOSTE도 "금색=패리, 붉은색=대시" 텔 시스템을 쓰며 보스 8종의 텔 타이밍이 config.js/보스별 로컬 테이블에 있는지는 실측 필요. **제안**: `node tools/boss-overlap.mjs` 류 자동 검증처럼, 보스별 패리 판정창(프레임 수) 편차를 한 곳에 모아 점검하는 스크립트가 이미 있는지 확인 후, 없다면 간단한 리포트만 추가(신규 밸런스 변경은 하지 않음).

4. **관찰**: 잼 심사에서 "체력바 등 UI 피드백 누락"이 실제 감점 사례로 지목된다 [[출처]](https://www.gamedeveloper.com/design/the-designer-s-notebook-how-should-we-judge-a-game-jam-). **RIPOSTE 상태와의 차이**: 손패 3슬롯, 랭크, 트라이 수 등 UI 요소가 화면에 실측 노출되는지 이번 조사에서는 확인하지 않았다(확인 필요, 코드 미열람). **제안**: 다음 QA 패스에서 스크린샷으로 UI 노출 여부만 확인 — 코드 변경 아님.

5. **관찰**: itch.io 페이지는 커버 630×500 + 스크린샷 3장 이상을 권장한다 [[출처]](https://hedgiespresso.itch.io/itch-page-image-templates). **RIPOSTE 상태와의 차이**: README에 스크린샷 4장(title/story/perfect-parry/mirror-phase2)이 이미 있으나 itch.io 페이지 자체가 없다(CLAUDE.md 명시). **제안**: itch.io 페이지 생성 시 해당 4장을 그대로 스크린샷으로 등록하고, 커버 1장만 630×500 비율로 추가 제작 — 최소 작업.

6. **관찰**: 심사 프레임은 "작지만 완성된 게임 > 크지만 미완성인 게임"을 명시한다 [[출처]](https://www.gamedeveloper.com/design/the-designer-s-notebook-how-should-we-judge-a-game-jam-). **RIPOSTE 상태와의 차이**: RIPOSTE는 보스 8종×2챕터, Phase 2, 대화+선택지까지 포함해 통상 잼 스코프(48~72시간) 대비 크다(현재 커밋 로그 기준 이미 상당 부분 구현 완료로 보임 — 실제 진행률은 확인 필요). **제안**: 잼 제출 마감 전에는 신규 콘텐츠 추가보다 기존 8보스의 완성도(버그·밸런스·판정 편차)를 우선 — 비목표(외부 에셋 등)와는 무관, 스코프 관리 문제.

7. **관찰**: itch.io는 임베드 캔버스가 "창 크기에 맞춰 반응형"이길 권장한다 [[출처]](https://itch.io/docs/creators/html5). **RIPOSTE 상태와의 차이**: RIPOSTE는 960×540 논리 해상도 고정(스펙 SSoT). **제안**: 반응형 리사이즈 자체는 비목표를 건드리지 않는 범위에서, itch.io 임베드 옵션의 뷰포트 값만 960×540으로 명시 지정(비율 유지, 내부 로직 변경 없음) — 이미 있는 `tools/check-pages.mjs`로 배포 후 렌더 확인.

8. **관찰**: 실제 포스트잼 데브로그(Dice Kick, Angus Defense, Super Screwballs)에서 가장 흔한 후속 조치는 "난이도 옵션/이지 모드 추가", "보스러시 모드 별도 추가"였다 [[출처]](https://bluemango.itch.io/dice-kick/devlog/408889/post-jam-update) [[출처]](https://dragonsisle.itch.io/angus-defense/devlog/1363452/post-jam-update). **RIPOSTE 상태와의 차이**: RIPOSTE는 "난이도는 의도적으로 높게(숙련 봇 전부 승리, 평균 봇 전부 패배)"를 설계 철학으로 명시하고 있어 이지 모드 부재가 의도된 선택이다. **제안(상충 명시)**: 잼 제출본에서 난이도를 낮추는 것은 현재 설계 철학과 정면으로 상충하므로 제안하지 않음 — 다만 "post-jam 로드맵" 메모에 이지 모드/난이도 옵션을 후보로만 기록해두는 것은 가능(지금 구현 요구 아님).

9. **관찰**: Disassembly Line 팀은 "게임은 훌륭한데 페이지가 평범해서 그냥 지나쳐졌다"는 실제 플레이테스터 피드백을 받았다 [[출처]](https://divadzeng.itch.io/disassembly-line/devlog/681794/brushing-up-our-game-post-jam-lessons-learned). **RIPOSTE 상태와의 차이**: RIPOSTE README는 조작표·보스표·테스트 하네스 설명까지 이미 잘 정리돼 있으나, 이 정보가 itch.io 페이지에는 아직 없다(확인 필요). **제안**: README의 조작표·보스표를 itch.io 페이지 설명란에 그대로 옮기는 것만으로 "첫인상" 리스크 상당 부분 해소 — 신규 콘텐츠 제작 없음.

10. **관찰**: Titan Souls·SUPERHOT·Baba Is You·Celeste 4개 사례 모두 "핵심 규칙 1개는 잼 버전부터 정식판까지 절대 바꾸지 않는다"는 공통점이 있다. **RIPOSTE 상태와의 차이**: RIPOSTE의 핵심 규칙("공격 0개, 패리로 훔쳐쓴다")은 이미 명확하고 후크로도 강하다 — 이 항목은 차이가 아니라 정합 확인. **제안**: 향후 잼 이후 확장(챕터 3, 보스 추가 등)을 고려하더라도 "플레이어 자기 공격 0개" 원칙만은 유지 — 이미 스펙 SSoT에 있는 원칙이므로 신규 작업 아님, 확장 로드맵 작성 시 이 축을 앵커로 삼으라는 참고.
